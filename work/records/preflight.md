# Preflight — engineering record

Primary repository: https://github.com/teamleaderleo/preflight

This file keeps the durable engineering stories. Moving performance numbers belong in [`preflight-live-performance.md`](preflight-live-performance.md); moving release status belongs in [`../current-state.md`](../current-state.md) and the Preflight repository itself.

That split is deliberate. Preflight changes too quickly for several Scrapbook files to each maintain a “current headline.”

## What the project is

Preflight is a performance launcher and desktop companion for heavily modded Starsector. It prepares deterministic work before launch, applies runtime shortcuts only when exact evidence still authorizes them, and falls back to the game's original path when a build, mod, class, or prepared artifact no longer matches.

The current development performance arc is roughly **101 seconds → 13.69 seconds** on the 83-mod M5 MacBook Air installation. An older same-session benchmark sample used only five runs per condition and recorded 89.00s ordinary versus 15.53s accelerated medians; retain it as historical context only. See the live performance record for the current frontier and career-facing usage.

## Why this is a strong engineering artifact

The interesting part is the combination:

- Java instrumentation and bytecode transformation against code the project does not own;
- performance work where cache validity is also a compatibility question;
- measurement built to distinguish critical-path work from misleading adjacent timing;
- prepared textures, data, audio, resource indexes, and generated bytecode;
- native desktop packaging, profiles/settings, diagnostics, support/privacy boundaries, update/rollback, and release evidence.

A shortcut only survives if Preflight can answer two questions: **is this work expensive enough to move?** and **what exact evidence makes reusing its answer valid?**

## Investigation stories

### The cache that sat behind a 27-second wait

An early prepared-pixel cache was valid and still barely moved launch time.

The useful response was measurement, not a larger cache. A critical-path probe showed the loading thread waiting roughly 27 seconds on a one-thread prefetch queue before the prepared work could help. Moving the intervention to the correct side of that wait turned essentially the same cached work into a major launch improvement.

The durable lesson is placement: an optimization can be correct, quick in isolation, and nearly irrelevant because another owner sits earlier on the path.

### The graphics-driver bottleneck that wasn't

Log gaps made one texture phase look like 13–18 seconds of graphics work. Preflight added seam timing that separated time inside the actual resource call from silence between calls.

A replay through the game's own LWJGL path later showed the launch's texture uploads using roughly 1.15 seconds of graphics-driver time. That killed the attractive “batch the GL work” story and reframed power-of-two padding mainly as memory/VRAM waste.

The instrumentation earned its keep because the preferred explanation lost.

### The filesystem syscall that was mostly path construction

Resource resolution could walk more than a million root/path combinations. Directory-list caching helped and substantial time remained.

Replay isolated roughly 2.393 seconds in repeated Java `File` construction and normalization across 1,185,072 joins. The eventual intervention moved upward to the point where root and relative path still existed separately, avoiding repeated normalized object construction before lookup.

The expensive thing was close to the syscall boundary without being the syscall.

### Case-insensitive lookup had to keep the filesystem in charge

A remembered-directory lookup originally compared filenames as strings. That broke valid resources on ordinary case-insensitive macOS/Windows filesystems when requested spelling differed from stored spelling.

The repair kept exact hits and misses cheap, then delegated the narrow folded-name ambiguity back to `File.exists()`, which remained the filesystem authority for that mount.

Performance work stayed subordinate to compatibility semantics.

### The command cache that looked larger than it was

Rule-command lookup appeared to spend hundreds of milliseconds searching failed package/class candidates. A prepared package map removed most failed probes and recovered only about 165ms.

Measurement showed the successful class load/verification/initialization dominated. The same investigation exposed a better target outside the game: six prepared-artifact caches rebuilt overlapping dependency identities before JVM launch.

One shared identity pass later reduced that launcher-side work from 1,612.6ms to 451.6ms while preserving all six resulting identities byte-for-byte.

### The digest memo that lost the trade

A per-file hash memo keyed by path, size, and mtime looked like an obvious optimization.

After parallelization, measuring first put the value around 65ms while the memo weakened detection of same-size content changes. The project kept full content hashing and removed duplicated passes instead.

A cheap optimization can still cost too much correctness.

### Audio: move pure decode, leave live ownership alone

The game decoded roughly 2,099 Ogg assets through a small worker pool and eventually made the main thread wait.

Simply widening the pool would also have widened concurrent access to OpenAL and an unsynchronized map. Preflight isolated the pure decoder seam instead: prepare exact decoded results outside the timed launch, retain the game's live OpenAL ownership and worker topology, and fall through to the original decoder when evidence differs.

### Generated Janino bytecode

Starsector/mod startup generates Java classes through Janino. Preflight built a complete generated-class-map cache whose identity covers compiler/version inputs, ordered source/archive inputs, classpath, JVM modules, parent loader, debug settings, and protection-domain policy.

A live pilot measured direct aggregate generation moving from 18.014s cold to 2.364s warm for 228 classes, with zero errors/corruptions/policy declines in the pair. Whole-launch movement was smaller, which is exactly why component and end-to-end numbers stay separate.

### Physical pack order became a performance contract

Later texture-storage work found that logical cache contents alone did not determine startup.

The same Compact corpus launched in 33.53s when written alphabetically and 14.174s when written in observed startup access order. Reordering an existing pack took 2.02s.

That result turned physical publication order into part of the prepared-pack contract. The learned Compact path also reduced steady-state texture data to roughly 1.1 GB on the measured profile.

## Compatibility model

Preflight's runtime interventions are gated by combinations of source/archive identity, class bytes or signatures, class loader, method descriptors/expected bytecode form, and the identity of the policy/input that produced prepared data.

Changed, corrupt, missing, or unsupported inputs decline the shortcut and return to ordinary game behavior. Runtime transformation lives only inside the child JVM; the project does not rewrite game or mod JARs, executables, assets, or saves.

The exact implementation has evolved. The stable idea is simpler: **cached speed never gets to silently outrank evidence about what is being executed.**

## Productization

Preflight moved well past a benchmark harness. Current product/source work includes:

- CLI plus native desktop host;
- automatic install discovery and launch;
- named mod profiles and prepared-data identity;
- common/extended launch settings;
- storage planning, repair, and cleanup;
- play-history tracking;
- deep read-only setup analysis and mod linting;
- privacy-bounded copy/support paths;
- signed update/rollback machinery;
- Windows, macOS, and Linux package/rehearsal work;
- machine-readable capability receipts for packaged native behavior.

Release claims belong to the exact candidate package generation that produced their evidence. Private rehearsal or development evidence cannot silently authorize later public bytes.
