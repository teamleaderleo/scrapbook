# Mainland game/runtime positioning review — Sol lens

**Status:** independent review artifact; not canonical résumé wording.  
**Baseline:** English V13, 2026-08-26, plus the current Preflight/open-source records.  
**Lens:** miHoYo / Tencent Games / NetEase client, runtime, performance, base-tech, and tooling teams.

## The profile has changed category

The older profile needed help proving depth. It read more like a strong early-career generalist: IBM internship, a broad set of owned projects, good technical instincts, and enough range that the résumé had to explain why the reader should take the projects seriously.

V13 no longer has that problem.

The current page has one flagship system with unusually legible game/runtime performance evidence, plus independent upstream work showing the same habits in unrelated mature codebases:

- Preflight: startup/loading, asset preparation, storage layout, JVM instrumentation, generated bytecode, high-frequency runtime work, VRAM/resource accounting, cross-platform packaging, updates and rollback;
- Cloud Hypervisor: VM lifecycle, boot failure propagation, VFIO mapping, QCOW metadata ownership and failure ordering;
- Vite / Cloudflare Workers SDK / Vercel AI SDK: teardown, temporary-resource ownership, stream cleanup, stale credentials, stateful runtime behavior;
- IBM: production-adjacent debugging, RBAC failure, Java test systems, cross-team repair, developer setup.

The Chinese résumé should stop presenting this as “a broad software engineer with several interesting projects.” The stronger thesis is:

> **性能 / 运行时 / 调试 / 故障处理 / 工具链工程师，旗舰项目恰好发生在一个真实的重度 Mod 游戏栈里。**

That is a much more specific and defensible profile.

## Positioning line

I would not use the seed's full five-part line as the default:

> 游戏运行时 / 性能优化 / 客户端基础设施 / 研发效能 / 跨平台工具

It feels like a keyword bouquet. `客户端基础设施` is also less natural for game hiring than `客户端基础技术` or a concrete `工具链`, and `研发效能` is useful only when the target team actually talks that way.

My default game-tech line would be:

> **方向：性能优化 / 游戏运行时与客户端基础技术 / 跨平台工具链**

For a performance-heavy role:

> **方向：游戏客户端性能优化 / 运行时与资源加载 / 调试工具**

For a tooling or engineering-productivity role:

> **方向：客户端工具链 / 构建与发布 / 性能与故障诊断**

Use `研发效能` when the role itself is an efficiency/platform role. Use the concrete mechanism everywhere else.

## Preflight should lead for game companies

Yes.

For a game/runtime reader, Preflight is more valuable above the fold than a row of recognizable OSS names. It answers the domain question immediately and then gives enough systems depth to keep the reader interested.

The heading in the current seed is close, but `JVM 性能启动器` sounds a little translated. I prefer:

> **Preflight — 游戏运行时性能优化与跨平台启动工具（个人开源项目）**

or, for a tooling-heavy role:

> **Preflight — 跨平台游戏启动、性能分析与 Mod 工具**

The first is stronger for client/runtime teams. The second is broader and more product-like.

The project should not try to look like UE/C++ experience. Its value is that it is a real game stack with real loading, runtime, resource, compatibility, packaging, and debugging constraints, and that the work goes deep enough to transfer.

## Preflight needs fewer numbers than the seed

The seed proves too much at once. A technical interviewer may enjoy every counter; an HR/recruiter pass will lose the line.

The numbers I would keep by default are:

- **112.17s → 13.69s / 8.19×** — flagship result;
- **83 个第三方 Mod** — scale and ecosystem context;
- **200.77s → 16.21s + 4.76 GB → ~1.1 GB** — preparation/storage story;
- **33.53s → 14.174s** on the same logical texture corpus when physical order changed — unusually good locality/I/O story when the target is performance-heavy;
- **1.22 GiB** VRAM padding removed — instantly legible for game/client teams;
- **36,332 → 280 / 145.96 MiB → 1.13 MiB / 1.501s → 29ms** — keep a compressed subset when runtime/bytecode work is important.

The 39,017 JSON calls / 8,378 paths / ~990k values and 227,805 / 79.1M / 117.9M counters are excellent interview evidence. I would not force all of them onto the default Chinese page.

### Keep

### Prefer plainer Chinese over code-switching

- `memoization` → **结果缓存** or **记忆化缓存**; default to `缓存` when the distinction is not important.
- `memoized read layer` → **共享读取/解析缓存层**.
- `loader cache` → **加载器缓存**.
- `merged-read overhead` → **合并读取开销**.
- `sector-wide O(n) entity scan` → **全局 O(n) 实体扫描**.
- `mutation-tracked index` → **增量索引** or **随状态变更维护的索引**.
- `commodity recomputation` → **状态未变化时的重复计算** unless the game-domain noun helps the target reader.
- `pack 发布流程` → **单包写入/持久化流程**. `发布` sounds like software release rather than storage publication.
- `onboarding` → **开发环境搭建** or **新人开发环境配置**.
- `hotfix` → **紧急修复**.
- `hybrid cloud / on-premises` → **混合云 / 本地部署**.

### Terms I would not make default headings

- `客户端基础设施` — prefer **客户端基础技术** or a concrete `客户端工具链`.
- `研发效能` — valid mainland terminology, but broad. Use it for platform/tooling teams that explicitly own developer efficiency.
- `性能启动器` — understandable, but awkward. Let the project be a `启动工具` whose engineering thesis is runtime performance.

I cannot verify the exact terminology from our older Chinese draft because that text is not present in the current repository history. Conceptually, I would restore the older/plain engineering instinct if it conflicts with the seed: **性能调优、客户端基础技术、工具链、故障定位** beat more corporate or translated labels.

## Section order

For miHoYo / Tencent Games / NetEase game-tech applications:

1. **核心项目** — Preflight
2. **开源贡献** — Cloud Hypervisor first, then a compressed tooling/runtime cluster
3. **实习经历** — IBM
4. **教育背景**
5. **技能**

`独立工程项目` is accurate, but `核心项目` gets to the point quicker. The Preflight heading can say `个人开源项目` so ownership remains explicit.

For a conventional non-game large-company application, IBM or OSS can move upward again. The game-targeted version should exploit the fact that the strongest current evidence is now directly game-adjacent.

## Compress the OSS section differently from English V13

The English V13 can afford to lead with named repositories because the page is also signaling broad open-source engineering.

For mainland game-tech, five separate brand rows are too name-heavy. The useful story is the mechanisms.

I would keep **Cloud Hypervisor** as its own row because four merged Rust/VMM repairs form a coherent low-level cluster. Then compress Vite / Cloudflare / AI SDK into one `运行时与工具链开源贡献` row or two short rows depending on the target.

React is the first cut for this audience.

A game-tech reader should come away thinking:

> this person can enter unfamiliar mature code, identify the actual state/resource owner, reproduce the failure, and make a small repair that survives review.

not:

> this person has collected five famous repository names.

## Current company lenses

These are positioning notes, not claims that every current opening has the same requirements. Recheck the exact role before sending a tailored résumé.

### miHoYo

Current game-client language strongly rewards core client modules, performance, memory/rendering/network bottlenecks, learning ability, game interest, open-source/GitHub work, and increasingly AI-assisted development.

Lead with:

- Preflight startup/loading and resource pipeline;
- runtime profiling and debugging across third-party code;
- VRAM/resource work;
- bytecode/runtime adaptation;
- cross-platform desktop packaging and updates;
- open-source work as proof that the debugging method transfers outside one personal codebase.

miHoYo also publicly emphasizes game industrialization pipelines and technical R&D. For tooling/base-tech teams, Preflight's packaging, diagnostics, mod analysis, compatibility and update path become more important than one more microbenchmark.

### Tencent Games

Current client/performance role language is almost a direct vocabulary map for the strongest Preflight evidence: CPU/GPU performance, memory/VRAM, loading, Bug/Crash diagnosis, performance monitoring, client toolchains and workflows. Launcher/client-infrastructure roles also care about SDKs, pipelines, cross-platform desktop behavior and project integration cost.

Lead with:

- performance diagnosis and bottleneck ownership;
- memory/VRAM and storage/layout work;
- cross-platform launcher/productization;
- failure handling and recovery;
- tooling that makes repeated engineering work cheaper;
- Cloud Hypervisor for lower-level lifecycle/storage correctness.

For Tencent, `客户端工具链` is usually more concrete than `研发效能` unless the target is explicitly a productivity platform.

### NetEase Games

Current client roles commonly emphasize client performance/logic/presentation optimization, engine maintenance/upgrades, online-game maintenance, debugging, and performance tuning; some also explicitly value AI coding/tool pipelines.

Lead with:

- performance and runtime debugging;
- compatibility/fallback behavior in a long-lived third-party game ecosystem;
- failure handling rather than benchmark-only optimization;
- storage/resource-loading work;
- IBM's production debugging/cross-team repair as a supporting professional signal;
- Cloud Hypervisor/Vite/Cloudflare as evidence of maintaining and repairing mature systems.

## The biggest screening gap is now obvious

The page does **not** advertise C++ or UE/Unity production experience.

A lot of mainland client/engine social-hire roles ask for exactly that, often with explicit years. The current profile should not blur this gap with wording. If there is real, defensible C++ experience that is simply missing from V13, surface it. If there is not, target roles where performance/runtime/tooling evidence can plausibly substitute for engine-specific tenure, and use Preflight as the proof of transfer.

The strong move is not to cosplay as a conventional three-year UE client engineer. The strong move is to make a technical hiring manager think:

> this person has already solved several of the classes of problems we care about, in a different stack, and learns unfamiliar systems unusually quickly.

## Skills should be reordered for the target

The current seed starts with TypeScript/JavaScript, which pushes the page back toward broad web/full-stack.

For a game/runtime variant, I would use something closer to:

> **语言：** Rust、Java、C、Python、TypeScript / JavaScript、Go、SQL  
> **系统与工具：** Linux、JVM、JFR、Tauri、Vite / Rolldown、Docker、Git、React、Cloudflare Workers

Only keep JFR if the final résumé is comfortable naming the profiling tool explicitly; the Preflight evidence supports it.

If a target role explicitly values AI Coding / Agent tooling, that can be added as a tailored skill or interview topic. I would not let it replace the technical work itself on the base game-tech résumé.
