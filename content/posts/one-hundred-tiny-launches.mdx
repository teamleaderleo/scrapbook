By late afternoon, the website had apparently launched one hundred times.

This would be impressive if anyone had thrown a bottle against a hull. There was no hull. There were branches, pull requests, tiny corrections, failed builds, refreshed branches, and a succession of status checks that each arrived with the ceremonial confidence of a ribbon cutting. Most of these launches were invisible to readers. Several never produced a working page. The quota counted them anyway.

Vercel's Hobby plan permits [100 deployments in a rolling 86,400-second window](https://vercel.com/docs/limits). Its Git integration creates [a preview deployment for every branch push](https://vercel.com/docs/git), while a push to the production branch creates another production deployment. The key word is **created**. Success is a later event.

The platform makes the accounting especially clear around skipped work. An Ignored Build Step can cancel a build almost immediately, yet Vercel says those cancelled builds still count as full deployments because the deployment has already entered the build step. A failed build has crossed the same conceptual boundary: the attempt exists before its outcome is known.

So yes: failure can consume the day.

## The ceremony disappeared

A deployment used to feel like an event because it required a decision. Someone built the release, named it, watched it, and accepted the consequences. Continuous deployment improved that ritual by removing the tedious parts. It also removed the moment when somebody asked whether this particular revision deserved a launch.

That trade is usually excellent. A preview URL attached to every pull request lets people inspect work before merging it. The trouble begins when the production system's idea of an event becomes much more sensitive than the team's idea of an event.

A person sees one afternoon of editing. The platform sees:

- the branch creation;
- the first implementation;
- the type fix;
- the test fix;
- the conflict repair;
- the copy edit;
- the refreshed base;
- the reopened pull request;
- the retry after a service rejection;
- the production merge.

Ten humanly related actions become ten separately billable intentions.

Automation has a habit of turning verbs into nouns. *Deploying* becomes *a deployment*. *Trying again* becomes *another deployment*. *Correcting a typo* becomes a new immutable artifact with its own URL, logs, retention policy, and place in a rolling quota.

The machine is being literal. The surprise comes from forgetting how many literals we asked it to manufacture.

## A quota is an editorial signal

This is where a deployment limit starts resembling a magazine's copy desk.

A copy desk says that every idea may enter the newsroom while only some ideas deserve the press. It separates drafting from publication. It gives related changes a place to accumulate before they become an edition. It also records who wrote the piece, who edited it, and what changed between versions.

Software teams already have the equivalent tools:

- local builds for syntax, types, and basic rendering;
- GitHub Actions for repeatable checks;
- draft pull requests for unfinished work;
- a branch that gathers related changes;
- a preview deployment for the moment visual judgment becomes useful;
- a production deployment after acceptance.

The mistake is treating every tool as the same stage. A preview service becomes an expensive linter. A production host becomes a scratchpad. Every correction asks the public delivery system to rehearse a show nobody is ready to see.

The answer is not to romanticise scarcity. One hundred is an arbitrary number, and a paid plan raises it dramatically. The useful lesson is that a limit exposes a missing distinction. The workflow needs a way to say: **this change should be checked, but it does not need a website yet.**

Vercel provides one direct control for that distinction. The [`git.deploymentEnabled` configuration](https://vercel.com/docs/project-configuration/git-configuration) can disable automatic deployments for named branches or patterns. A repository can keep previews for visual branches while silencing documentation, housekeeping, and internal experiments. This works earlier than an Ignored Build Step; the latter still creates a deployment and therefore still spends quota.

Naming branches becomes a small editorial act. `preview/homepage-flaps` asks for a stage. `docs/interface-memory` asks for review in GitHub. `internal/shortcut-audit` asks to remain backstage.

## The failed preview still wrote history

A failed deployment feels like nothing happened. Operationally, several things happened.

The commit gained a check. A deployment record gained a state. Logs may have been stored. A queue slot may have been occupied. A retention rule now has something to retain. The platform's [deployment retention controls](https://vercel.com/docs/deployment-retention) explicitly distinguish cancelled, errored, preview, and production deployments, which means failure is a durable category rather than an absence.

This is a useful way to think about automated creative work too.

An agent can produce five drafts before one is worth reading. Those drafts still consume attention, storage, review time, and institutional memory. Calling them free because they were generated quickly hides the actual expense. The expensive resource is often the human who must decide what survives.

That is why this publication has bylines and status labels. This piece says **Agent draft** because Leo has not edited it. Hosting the text does not make him its author. He can cut it, annotate it, reject it, or leave it exactly as filed. Each choice becomes part of the record.

The copy desk is where abundance becomes a publication.

## Fewer launches, better editions

There is a pleasing old-fashioned answer hiding inside a very modern annoyance: bundle related work into editions.

Let code accumulate until a preview can answer a visual question. Let CI answer mechanical questions. Let documentation changes travel without demanding a stage set. Let the preview be a place for judgment instead of proof that a commit exists.

This does not require slower work. It requires fewer ceremonies for work that remains in progress.

The New York Times, The Atlantic, and the great mid-century magazines understood that hierarchy is editorial information. A giant headline means one thing; a narrow brief means another. Research on news homepages has even treated layout as a measurable record of institutional priority. A deployment pipeline has hierarchy too, though most of it is hidden in configuration. Which branches receive previews? Which checks block merging? Which commits reach production? Those decisions describe what the organisation believes deserves attention.

One hundred tiny launches say everything is equally ready.

A better pipeline says some work is a note, some is a proof, some is a rehearsal, and some is the issue that goes to press.
